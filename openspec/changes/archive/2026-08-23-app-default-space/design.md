## Context

`internal/layout/restore.go`'s `planFallbackMoves` currently computes, per bundle ID, a fallback target purely from `validAssignmentOrdinals` (the ordinals of that bundle's valid direct matches this restore) via `fallbackTargetForAssignments`, and is only invoked for bundle IDs present in that map — i.e. bundles with at least one valid direct match (see `planLayoutPhase` in the same file, and the "Restore matches windows by title, falling back to index" requirement in `openspec/specs/space-layout/spec.md`). `internal/config/config.go` already has an established pattern for a per-display-count, per-bundle config setting (`Pins`/`PinRule`, with `pinRuleFileFormat`/`validatePins`) that this change's `default_spaces` setting will mirror closely. See `proposal.md` - Why for the motivation; this doc covers how the new setting plugs into `planFallbackMoves`'s existing call site without restructuring `Restore`'s two-phase pin/layout orchestration.

## Goals / Non-Goals

**Goals:**
- Reuse `config.go`'s existing `pins`-style parsing/validation pattern for `default_spaces`, so the two settings read consistently in `config.yaml` and require no new validation machinery.
- Change only `planFallbackMoves`'s target-selection step and its "only when the bundle has ≥1 valid assignment" gate; leave `planDirectMoves`, `matchEntries`, and the pin-phase orchestration in `Restore` untouched.
- Make the configured-default's "always wins" precedence over the prevalent-Space heuristic a simple, easy-to-read conditional at the top of the per-bundle fallback-target resolution, not a scoring/merging scheme.

**Non-Goals:**
- No per-window or per-title default (that's what `pins` is for) — `default_spaces` is strictly application-level, exactly like the existing prevalent-Space fallback it augments.
- No interaction with `pin_precedence` — a configured default space only ever affects the *layout phase's* application-level fallback step (windows left over after both pin matching and saved-entry matching), never the pin-matching phase itself, regardless of `pin_precedence`'s pin-vs-layout ordering.
- No CLI for managing `default_spaces` — `config.yaml` hand-editing only, matching `pins`.

## Decisions

- **`default_spaces` YAML shape: `map[int][]DefaultSpaceRule`, `DefaultSpaceRule{BundleID string, Space int}`.** Keyed by display count exactly like `pins`, so it reads naturally next to it in `config.yaml` and reuses the same `map[int][]T` parsing shape (a new `defaultSpaceRuleFileFormat` and `validateDefaultSpaces` alongside `pinRuleFileFormat`/`validatePins`). No `Title` field — this rule is per-application, not per-window. Alternative considered: reusing `PinRule` with an ignored `Title` — rejected because a required-but-ignored field would confuse users editing the file by hand.
- **Resolve the configured default inside `planFallbackMoves`, as a lookup passed in by `Restore`.** `Restore` already loads `config.Config` (via its caller in `cmd/mumu/cmd/layout.go`) and already threads `cfg.Pins[displayCount]`/`cfg.PinPrecedence` into `Restore`'s signature; this change adds a parallel `defaultSpaces []config.DefaultSpaceRule` parameter (or an already-indexed `map[string]int` — see below), threaded through `planLayoutPhase` into `planFallbackMoves`, converted to a `map[string]int` (bundle ID → target ordinal) once per `Restore` call rather than re-scanned per bundle. Alternative considered: resolving it earlier in `Restore` and pre-seeding `validAssignmentOrdinals` with a synthetic single-entry list — rejected because it would make a configured default indistinguishable from a real (non-tied) prevalent assignment in the "most prevalent" tie-detection logic, and because `fallbackTargetForAssignments`'s tie/no-tie branching has no natural way to express "this always wins, full stop."
- **`planFallbackMoves` iterates the union of `assignmentOrdinals` keys and `defaultSpaces` keys, not just `assignmentOrdinals` keys.** This is the one-line change that lifts the "requires ≥1 valid assignment" gate for bundles with a configured default: today's loop is `for _, bundleID := range bundleIDs` where `bundleIDs` comes only from `assignmentOrdinals`; the new version unions in every bundle ID with a configured default, then for each bundle ID checks "does `defaultSpaces` have this bundle ID?" first (configured-default wins unconditionally) before falling through to `fallbackTargetForAssignments`'s existing prevalent/tie/primary-display logic.
- **A configured-default placement reports distinctly from a prevalent-Space placement in restore output**, via a new `moveTarget`/`SkippedEntry` marker (e.g. a `defaultConfigured bool` alongside the existing `fallback bool`, since a configured-default placement is still fundamentally a "fallback" in the sense of not being a direct title match — it reuses `Fallback: true` for skip-reporting purposes but adds its own progress-line marker like the existing `(fallback)`/`(fuzzy)` markers) so a user can tell the two apart in `mumu restore` output. Alternative considered: a silent, unmarked placement — rejected because it would make configured-default behavior indistinguishable from the heuristic it's overriding, undermining the predictability this feature exists to provide.
- **`mumu show`'s `default_spaces` listing is unresolved config, not a live-matched preview**, printing raw `{bundle_id, space}` pairs with `space.DualLabel`, mirroring the existing pin-preview's `printConfiguredPins` (new `printConfiguredDefaultSpaces` alongside it in `cmd/mumu/cmd/layout.go`) for the same reasons `mumu show`'s pin preview avoids live matching (fast, side-effect-free, never goes stale before an actual restore runs).

## Risks / Trade-offs

- Two independent config settings (`pins`, `default_spaces`) both keyed by bundle ID but serving different roles (per-window vs. application-level fallback) could read as redundant to a user skimming `config.yaml` → Mitigated by keeping their YAML shapes visibly distinct (`pins` entries have `title`; `default_spaces` entries don't) and documenting the distinction explicitly in `docs/CONFIG_SCHEMA.md` and the default-generated config comments.
- Lifting the "≥1 valid assignment" gate for bundles with a configured default means an application that's running but has never been captured in any saved layout for the current display count can now have all its open windows moved on `mumu restore`, which is a behavior change for anyone who configures `default_spaces` → Mitigated by this being strictly opt-in (only activates for bundle IDs explicitly configured) and documented plainly in the proposal and `docs/CONFIG_SCHEMA.md`.
