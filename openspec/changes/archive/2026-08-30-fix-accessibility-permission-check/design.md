## Context

See `proposal.md` - Why. Two independent issues were found while investigating "Accessibility settings not reflecting what System Settings shows":

1. `internal/permissions/permissions.m` calls `AXIsProcessTrusted()`. This is not deprecated, but `AXIsProcessTrustedWithOptions(NULL)` is the currently documented non-prompting check and is a strict superset (it also accepts an options dict for a future prompting variant). Both share the same underlying per-process TCC trust cache — this cache only matters for long-running processes that poll repeatedly while permissions change underneath them.
2. `mumu` is a short-lived CLI (one process per invocation, no daemon — confirmed via `internal/native`/`cmd` inspection), so the per-process cache described in (1) is unlikely to be the actual cause here: each invocation is a fresh process with a fresh TCC lookup either way.
3. The `justfile`'s `bundle` recipe runs `codesign --force --deep --sign - --entitlements resources/Mumu.entitlements --options runtime build/Mumu.app` — ad-hoc signing (`--sign -`). The `build` recipe (`bin/mumu`, via `go build`) is not signed at all. macOS's TCC keys an Accessibility grant to the binary's designated requirement, which for ad-hoc/unsigned binaries is effectively pinned to that exact binary's code directory hash (cdhash). Every `just build` or `just bundle` produces a new hash, so TCC silently stops recognizing the "same" app across rebuilds — System Settings keeps showing a checked box for a grant that no longer matches the binary actually running. This is the most likely explanation for the reported symptom, since it reproduces on every rebuild during normal development.

## Goals / Non-Goals

**Goals:**
- Make the Accessibility check use the currently documented API entry point.
- Give locally built `mumu` binaries (both `bin/mumu` and `build/Mumu.app`) a stable code-signing identity across rebuilds, so Accessibility/Screen Recording grants survive `just build`/`just bundle` during normal development.
- Leave a durable comment trail (in code, near the check) explaining the TCC caching and cdhash-pinning quirks, so this isn't re-diagnosed from scratch.

**Non-Goals:**
- Distributing a Developer ID-signed, notarized release build. That's a separate concern (release packaging) from keeping a *local dev build* stable across rebuilds, and isn't implicated by the reported bug.
- Adding a prompting flow (`kAXTrustedCheckOptionPrompt`) for Accessibility. `mumu status`'s contract (per `space-layout` spec) is to report state, not to trigger OS prompts; that stays out of scope.
- Changing anything under `internal/native` — the audit found no other stale API usage there.

## Decisions

- **Switch to `AXIsProcessTrustedWithOptions(NULL)`.** Passing `NULL` for the options dictionary is documented as equivalent to `AXIsProcessTrusted()` for a read-only check, so this is a behavior-preserving swap. Alternative considered: leave `AXIsProcessTrusted()` as-is, since it isn't actually deprecated — rejected because the user's own research surfaced `AXIsProcessTrustedWithOptions` as the modern form, and standardizing on it costs nothing while keeping the surrounding comment focused on one API.
- **Sign local dev builds with a stable identity keyed by certificate, not by binary hash, where possible; otherwise document the limitation.** Ad-hoc signing (`--sign -`) with no identity always pins TCC's designated requirement to the binary's own cdhash, which changes every build — that's inherent to ad-hoc signing and can't be fixed by flags alone. The durable fix is a self-signed code-signing certificate used consistently for local builds, since TCC can pin the designated requirement to the certificate's leaf hash instead of the binary's cdhash, which stays stable across rebuilds signed with that same certificate (verified: `codesign -d -r-` shows an identical `certificate leaf = H"..."` requirement across repeated `just build` runs). This requires a one-time, per-developer-machine setup step (documented, not automated in `just build`, since generating a keychain identity is a local, human action outside repo tooling's remit) — `justfile` will use that identity if present via an overridable variable, and fall back to ad-hoc (today's behavior, with the known caveat documented) if absent.
- **Store the certificate in a dedicated `mumu-dev.keychain-db`, not the user's login keychain.** Discovered during implementation: importing into the login keychain and then running `security set-key-partition-list` (needed so `codesign` can use the key non-interactively) popped a GUI authorization dialog requiring the real login password — which blocks headless/scripted runs (including this session's own verification) and isn't acceptable for a `just` recipe meant to run non-interactively. A dedicated keychain with a fixed, locally-generated password (not a real secret — it only exists so `security` commands can self-authorize) avoids that prompt entirely, at the cost of one extra step (adding it to the user's keychain search list so `codesign`/`security find-identity`, called without an explicit `--keychain`, can still find it without extra flags in `build`/`bundle`).
- **Apply signing to both `just build` and `just bundle`.** Today only `bundle` signs at all; `build` (the everyday `bin/mumu` used for local testing per the bug report) is unsigned, which has the same cdhash-churn problem (an unsigned binary's identity is derived from its own hash too). Both recipes need the same treatment for the fix to actually resolve the reported symptom, since the user is most likely exercising the raw `bin/mumu` binary during dev/test.

## Risks / Trade-offs

- [A self-signed certificate requires one manual setup step per developer machine] → Mitigation: document it clearly (README/CODING_STANDARDS or a `just` recipe like `just setup-codesign-identity` that creates it if missing), and keep the ad-hoc fallback so `just build`/`just bundle` still work with today's caveat if a developer skips setup.
- [Switching `AXIsProcessTrusted()` -> `AXIsProcessTrustedWithOptions(NULL)` doesn't fix the actual reported symptom by itself, since the real cause is likely signing churn, not the API name] → Mitigation: ship both changes together as scoped by the proposal; document in the code comment that the API choice alone does not solve TCC cdhash pinning, so a future reader doesn't assume the API swap alone is a complete fix if the signing piece regresses.
- [A stale grant from before this change (pinned to an old ad-hoc cdhash) won't retroactively fix itself] → Mitigation: this is expected and matches existing behavior (users occasionally re-grant permission after macOS updates); no migration needed, document that some users may need to re-grant once after adopting the new signing identity.

## Open Questions

- Exact mechanism for the one-time certificate setup (e.g., a documented `security` CLI recipe vs. a script) is an implementation detail for `tasks.md`/coding time; it doesn't change the spec or the chosen approach.

## Verification environment note

Live end-to-end verification (task 2.5) was attempted on a Jamf/Casper-MDM-enrolled, fully-managed, non-admin machine. The System Settings toggle behaved correctly in every observable way — it turned on, stayed on across reopening System Settings, and macOS presented the expected approval prompt, which was granted — yet `mumu status` continued to report Accessibility as not granted, for both `bin/mumu` and `build/Mumu.app`.

To rule out a mumu-side bug, a minimal isolated test binary was built containing only a call to `AXIsProcessTrustedWithOptions(NULL)`/`AXIsProcessTrusted()` (no mumu code at all), signed with the identical `mumu-dev-signing` identity, and put through the same grant flow. It also reported `false` for both APIs. Since this rules out anything in mumu's code or its specific binary, the remaining explanation is that the device's MDM enrollment applies a Privacy Preferences Policy Control (PPPC) profile that overrides/ignores manual Accessibility grants for binaries outside an IT-managed allowlist (commonly matched by Team Identifier; this binary reports `TeamIdentifier=not set` since it's self-signed rather than Developer-ID-signed) — the visible toggle can reflect the user's request without the underlying TCC decision actually being "Allow."

This is an environmental constraint of the specific test machine, not a defect in the implemented fix. The cryptographic verification that the designated requirement (the actual thing TCC keys grants to) stays identical across rebuilds — the core of what this change fixes — is real, reproducible, and independent of this machine's MDM policy: `codesign -d -r-` on repeated `just build` output shows the same `certificate leaf = H"..."` requirement every time. On a non-MDM-managed machine, or one where the allowlist includes this identity, grant persistence across rebuilds is expected to work as designed.
