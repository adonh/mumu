## Context

See `proposal.md` for motivation. `mimi layout show` currently sorts `layout.Entry` values inline in `cmd/mimi/cmd/layout.go` (by `Ordinal` then `BundleID`); `mimi layout restore` (`internal/layout/restore.go`) doesn't sort at all — it iterates `saved.Entries` (and therefore builds `toMove` and the skip list) in whatever order the layout file stores them, which is capture-time native enumeration order. Three call sites need the same ordering logic applied to `layout.Entry`-shaped data: `show`'s entry list (`cmd` package), restore's per-window move progress (`internal/layout` package, since progress is emitted inline with each move), and restore's skip summary grouped listing (`cmd` package again). The "macOS Space number" concept these sorts need to reference was just added by the `layout-native-space-labels` change (`space.LogicalSpaceID` / `space.MissionControlIndexForSpace` / `space.DualLabel`).

## Goals / Non-Goals

**Goals:**
- One sort implementation, usable identically from `cmd/mimi/cmd/layout.go` (for `show`'s list and restore's skip summary) and from `internal/layout/restore.go` (for restore's per-window move order, which must be decided before progress lines are emitted, inside `Restore` itself).
- Deterministic output for every `--sort` value, including when the primary key ties across multiple entries.
- Resolving the macOS Mission Control ordinal for `--sort macos` shouldn't repeat native lookups needlessly when many entries share the same saved Space (a common case — a whole desk's worth of windows on one Space).

**Non-Goals:**
- Resolving a human-readable application display name for `--sort app`; it sorts by the raw bundle identifier (per the interview decision), which mimi already uses as the app identity everywhere else in its output.
- Changing restore's window-matching or move logic, or the saved layout JSON schema — sorting is applied only to the order entries are *processed for display purposes* (skip detection and matching still happen per the existing per-entry loop; only the printed/moved order changes).

## Decisions

**Add `SortKey` (type) and `SortEntries` (function) to `internal/layout`, not `cmd/mimi/cmd/layout.go`.** `Entry` already lives in `internal/layout`, and `internal/layout/restore.go` needs to sort its internal `[]moveTarget` (each wrapping an `Entry`) before emitting per-window progress lines — that sort has to happen inside `Restore()`, in the `layout` package, so it can order the move loop itself, not just cosmetically re-order already-emitted lines. Putting the shared comparator in `internal/layout` lets `Restore()` use it directly (as an unexported helper shared with `SortEntries`) while `cmd/mimi/cmd/layout.go` calls the exported `layout.SortEntries()` for `show`'s list and for each skip-reason group in the restore summary. This mirrors the existing `layout-native-space-labels` change's placement of `space.DualLabel` in the lowest package that has natural ownership of the concept, rather than defaulting to the CLI layer.
_Alternative considered_: keep sorting purely in the CLI layer and have `Restore()` return `toMove` order unchanged, with the CLI only reordering how progress lines are *displayed* after the fact. Rejected: progress lines are emitted synchronously as each move happens (`progress.emit(...)` immediately before `window.MoveWindowIDToSpace(...)`), so the *move itself* would still happen in capture-time order even if a later display step reordered lines — misleading (a line claiming "space 3" was moved third could actually have been moved first). Sorting has to happen before the move loop runs, inside `Restore()`.

**`SortKey` is `type SortKey string` with constants `SortByDisplay = "display"`, `SortByMacOS = "macos"`, `SortByApp = "app"`, plus `ParseSortKey(raw string) (SortKey, error)` in the same file.** String-backed so it round-trips directly to/from the `--sort` flag's raw value with no separate mapping table; `ParseSortKey` centralizes validation (rejecting anything else with a clear error) next to the type it validates, the same way Go's standard library pairs enum-like types with a `Parse`-style constructor. The CLI flag's default is `SortByDisplay`.
_Alternative considered_: validate the raw string ad hoc in `cmd/mimi/cmd/layout.go`, matching how `resolveDisplayCountArg` validates its own argument locally. Rejected: `SortKey` validation isn't CLI-specific (a future non-CLI caller of `internal/layout` would need the same rule), and colocating `Parse` with the type is more idiomatic than duplicating a switch statement per call site.

**Comparator: primary key first, then always cascade Space ordinal → bundle identifier → window title, regardless of which key is primary.** Implemented as one unexported `entryLess(a, b Entry, key SortKey, mcOrdinal func(int) int) bool` used by both `SortEntries` (for `[]Entry`) and `Restore`'s internal sort of `[]moveTarget` (called with `.entry` from each side). For `SortByDisplay`, the primary check *is* the first cascade step, so no special case is needed — the switch only needs an explicit branch for `SortByMacOS` and `SortByApp` before falling into the shared three-step cascade.

**Mission Control ordinal resolution is memoized per distinct logical `Ordinal` value for the duration of one sort call.** `--sort macos` needs each entry's current Mission Control ordinal, which costs two native round-trips per lookup (`space.LogicalSpaceID` then `space.MissionControlIndexForSpace`, the same pair `space.DualLabel` uses for display). A sort compares many pairs, and typical saved layouts have many entries sharing the same `Ordinal` (several windows on one Space), so a small `map[int]int` cache keyed by `Ordinal`, built fresh for each `SortEntries`/restore-sort call, avoids redundant native calls without needing any persistent or cross-call cache.
_Alternative considered_: no memoization, resolving Mission Control ordinal freshly per comparison. Rejected as unnecessary native round-trips for large layouts with many same-Space entries — negligible correctness risk either way, but memoizing is nearly free to add and avoids the question entirely.

**`--sort` is a separate `StringVar` flag registered on both `layoutShowCmd` and `layoutRestoreCmd`, sharing one registration helper.** Cobra flags are per-command, so the two commands need their own backing variables (`layoutShowSort`, `layoutRestoreSort`), following the existing pattern of command-scoped package vars (e.g. `layoutRestoreAssumeYes`). A small `addSortFlag(cmd *cobra.Command, dest *string)` helper avoids duplicating the flag's help text and default value string between the two `init()` registrations.

**Restore's default order changes from capture-time order to `SortByDisplay`.** Per the interview decision, no flag passed means `SortByDisplay` is used explicitly (not "whatever order the file happens to store entries in") — this is what actually fixes the "arbitrary" behavior the proposal is about, since previously even `show`'s already-sorted default gave users a false impression that layout output is generally ordered.

## Risks / Trade-offs

- **Restore's default output order is a (cosmetic, non-breaking-in-effect) behavior change**: any script or muscle-memory workflow relying on the exact previous capture-order sequence of restore's progress lines will see different line order. No functional effect (matching/moving/skip logic is untouched), and the proposal calls this out explicitly as an intentional fix rather than a side effect.
- **`--sort macos` can still show `mcOrdinal == 0`-driven grouping for entries whose saved Space no longer exists** (same "Space not found" case `space.DualLabel` already falls back to `unknown` for in display text) — those entries sort as if their Mission Control ordinal were `0`, i.e. first. This is a pre-existing edge case (`SkipOrdinalOutOfRange`) and doesn't need special handling beyond what already exists: the entry still prints with `(macOS space unknown)` per the previous change, just first in `macos`-sorted order.
