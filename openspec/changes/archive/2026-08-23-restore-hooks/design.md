## Context

`internal/config/config.go` currently parses `config.yaml` into a flat `Config{DataDir, Pins, PinPrecedence}` via a `fileFormat` struct, with per-key validation functions (`validatePins`, `validatePinPrecedence`) called from `Load()`. `cmd/mumu/cmd/layout.go`'s `layoutRestoreCmd.RunE` loads config, checks arrangement drift (prompting unless `--yes`), then calls `layout.Restore(...)` and prints the summary; `layoutShowCmd.RunE` similarly loads config and prints the saved layout plus `printConfiguredPins`. See `proposal.md` - Why for the motivation; this doc covers how hook configuration and execution plug into that existing command flow.

## Goals / Non-Goals

**Goals:**
- Keep hook execution entirely at the CLI command layer (`cmd/mumu/cmd`), so `internal/layout` stays concerned only with window/Space matching and moving, not process execution.
- Follow `config.yaml`'s existing auto-create-with-defaults, never-silently-fall-back, clear-path-naming-error validation pattern already established for `pins`/`pin_precedence`.
- Make the four-array bracketing order (global off, layout off, layout on, global on) a single, testable resolution function shared by both `mumu restore` (to execute) and `mumu show` (to preview), so they can never disagree on order.

**Non-Goals:**
- No templating/interpolation inside command strings (no `{display_count}`-style placeholders) — a command that needs the display count can inspect its own environment or call `mumu` itself.
- No per-command timeout or overall hook-phase timeout — commands run to completion; a hung command hangs `mumu restore` the same way a hung command would hang any shell script invoking it.
- No change to `mumu save` — hooks are restore-only, per the `restore-hooks` spec's "no independent trigger" requirement.
- No structured hook results in `RestoreSummary` (e.g. no `HooksRun`/`HooksFailed` counters) — command success/failure is reported as it happens via the same progress-line mechanism restore already uses, not aggregated into the final summary. Revisit if a later change needs it.

## Decisions

- **New `internal/hooks` package, not folded into `internal/layout`.** `internal/layout` has no existing notion of spawning external processes, and pins deliberately reused its matching machinery because pins *are* window-matching. Hooks aren't — they're arbitrary process execution wrapping a restore, an orthogonal concern. A small package (`Run(commands []config.Command, progress func(string)) []Result` or similar, taking a progress callback the same shape `layout.Restore` already uses) keeps that separation and stays trivially unit-testable (inject a fake `exec.Cmd`-producing function, or shell out to `true`/`false`/`echo` in tests).
- **`config.Command` models "shell string or argv list" as one type with two mutually-exclusive fields, decoded via a custom `UnmarshalYAML`.** `Command{Shell string; Argv []string}` — exactly one populated. A custom unmarshaler inspects the YAML node kind (`ScalarNode` → `Shell`, `SequenceNode` → `Argv`) so `config.yaml` can mix plain strings and list entries in the same array without a wrapper key. Alternative considered: a `map[string]any`-style tagged union (e.g. `{shell: "..."}` or `{argv: [...]}`) — rejected as more verbose for the common case (a single shell string) that most users will reach for first.
- **`Hooks{Off, On []Command}` at both the global and per-display-count level, mirroring `Pins`' `map[int][]PinRule]` shape.** `Config` gains `Hooks Hooks` (global) and `LayoutHooks map[int]Hooks` (per-display-count), matching how `Pins` is already `map[int][]PinRule` — a reader familiar with `pins` immediately recognizes the `hooks.layouts.<n>` shape. `pin_precedence` is a flat top-level key because it's a single global toggle; `hooks`' global arrays are top-level within the `hooks:` block itself (`hooks.off`/`hooks.on`) since, unlike precedence, they're actual data (command lists), not a mode switch.
- **A single `resolveHooks(cfg *config.Config, displayCount int) (off, on []config.Command)` helper computes the four-array bracketing order once**, called identically by `mumu restore` (to run the result) and `mumu show` (to print it), so the two can never drift apart. It concatenates `cfg.Hooks.Off` + `cfg.LayoutHooks[displayCount].Off` for `off`, and `cfg.LayoutHooks[displayCount].On` + `cfg.Hooks.On` for `on` — no unexported ordering logic duplicated between the two call sites.
- **Hook execution wraps the existing `layout.Restore` call directly inside `layoutRestoreCmd.RunE`, after the no-saved-layout and drift-decline early returns.** This is the simplest way to satisfy "hooks only run when restore actually proceeds" without teaching `internal/layout` anything about hooks: by the time `RunE` reaches the `layout.Restore(...)` call, both bail-out conditions have already returned. `--no-hooks` is checked once at the top of that block, skipping straight to `layout.Restore(...)` when set.
- **`sh -c` (not `bash -c`) for shell-string commands**, since `/bin/sh` is guaranteed present on every macOS install mumu targets (per `AGENTS.md`'s no-elevated-privileges, minimal-dependency stance) and matches the portable-script convention already used for `.envrc`. A user who wants bash-specific syntax can write `["bash", "-c", "..."]` as an explicit argv command instead.
- **Failure reporting inline via the same progress callback restore already threads through**, printing something like `✗ command failed (exit 1): <command>` immediately when it happens, rather than deferring to a final summary — consistent with `log_and_continue` semantics and with how `layout.Restore` already emits per-window progress lines rather than only a final tally.

## Risks / Trade-offs

- A misconfigured or slow hook command (e.g. a typo'd binary, or a script that blocks on input) stalls `mumu restore` indefinitely since there's no timeout → Mitigated by streaming output live (a hung command's silence is visible immediately) and documenting in `docs/CLI.md` that hook commands should be non-interactive and fast; `--no-hooks` gives an immediate escape hatch for a one-off restore.
- Splitting hook resolution into a shared `resolveHooks` helper only pays off if both call sites (`mumu restore`, `mumu show`) are updated together — a future change to one without the other would silently desync the preview from actual behavior → Mitigated by making `resolveHooks` the only place either call site is allowed to compute the four-array order, covered by a unit test asserting both consumers get identical results for the same config/display count.
- Accepting arbitrary shell strings from `config.yaml` means a user who shares their config file also shares an arbitrary-code-execution vector → Mitigated by this being explicit, user-authored local configuration (the same trust boundary `data_dir`, `pins`, and the rest of `config.yaml` already sit inside), not something mumu fetches or executes from an untrusted source; documented plainly in `docs/CONFIG_SCHEMA.md`.
